# 二维投影与视觉模型技战术分析边界

更新日期：2026-09-16

## 1. 文档目的

本文档结合以下现有资料和代码能力，明确足球技战术分析中二维球场投影与视觉模型的适用边界：

- `足球技战术分析调研.md`
- `足球技战术分析最终优先级总结.md`
- `docs/L1事件层初步复现范围.md`
- `docs/tactical_analysis_framework.md`
- 当前 `tactical_analysis/` 分析器

这里的“视觉模型”包括图像多模态模型、视频多模态模型、动作识别模型和姿态估计模型。类似通用大模型 API 的服务只有在所选模型明确支持图片或视频输入时，才能承担视觉复核；纯文本模型不能直接理解比赛画面。

## 2. 核心结论

二维投影和视觉模型解决的是不同问题：

| 信息来源 | 最擅长回答的问题 | 典型输出 |
| --- | --- | --- |
| 二维球场投影 | 在哪里、相距多远、人数多少、队形如何变化 | 坐标、距离、速度、宽度、纵深、线距、区域人数 |
| 原始图像 | 是谁、穿什么、接触了什么、画面显示了什么结果 | 球队/角色、触球部位、动作类别、记分牌、裁判信号 |
| 多帧视频 | 动作何时开始、如何演变、前因后果是什么 | 射门、传球、扑救、对抗、球权变化、战术片段 |
| 姿态关键点 | 身体各关节如何运动 | 支撑脚、摆腿、躯干倾角、手臂展开、起跳和落地 |
| 官方事件/OCR | 比赛结果和管理事实 | 进球、比分、红黄牌、换人、比赛时间 |

因此推荐采用以下原则：

> 二维轨迹负责候选发现和数值计算，视觉模型负责动作语义和结果确认，官方标签或 OCR 负责比赛事实校准。

不建议把完整比赛直接交给通用视觉大模型，让模型从头生成全部技战术结论。更可靠的方式是先由本地检测、跟踪和二维分析筛出短片段，再让视觉模型复核。

## 3. 分类标准

本文将技战术能力分成三类。

### A 类：二维投影可以直接计算

前提是球员、球队、足球、球场标定和轨迹已经足够准确。输出应以客观数值为主，不要求视觉模型理解动作语义。

### B 类：二维投影生成候选，必须结合视觉复核

二维轨迹能够找到疑似事件或计算空间特征，但无法可靠确认动作类别、执行者、真实发生时刻或结果。该类最适合优先接入视觉 API。

### C 类：必须以视觉图片或视频分析为主

任务依赖人体姿态、身体接触、球的空中状态、裁判信号或复杂语义。二维坐标只能提供上下文，不能作为最终判据。

## 4. A 类：可直接由二维投影计算的能力

| 板块 | 技战术指标 | 二维计算方法 | 使用条件与边界 |
| --- | --- | --- | --- |
| 区域 | 球员/足球所在三区 | 按标准球场坐标划分后场、中场、前场 | 需要统一球队进攻方向 |
| 区域 | 左路、中路、右路分布 | 按球场横向坐标分区统计 | 只能说明空间分布，不能说明战术意图 |
| 区域 | 禁区内外、肋部、边路进入 | 点是否落在预定义多边形内 | 依赖准确标定和可见性 |
| 空间 | 平均站位 | 按球员轨迹或角色聚合坐标 | 跨镜头 ID 不稳时只能称轨迹平均站位 |
| 队形 | 宽度、纵深、重心高度 | 计算同队坐标范围、中位数或分位数 | 应按有球/无球和比赛阶段分别统计 |
| 队形 | 后卫线、中场线、前锋线线距 | 对纵向坐标聚类并计算层间距离 | 需要足够可见球员和稳定进攻方向 |
| 队形 | 紧凑度、凸包面积 | 计算球员凸包、面积和长宽比例 | 转播视野不完整会低估真实面积 |
| 阵型 | 阵型倾向 | 多帧层次聚类与阵型模板投票 | 只能输出倾向，不能凭单帧认定整场阵型 |
| 人数关系 | 局部多打少 | 在球或指定区域周围统计双方人数 | 反映数量关系，不等于形成有效进攻优势 |
| 防守 | 防线高度 | 防守方最后一线球员纵向位置 | 门将应排除，漏检会造成明显偏差 |
| 防守 | 线间空间大小 | 计算相邻防守线之间的距离和面积 | “空间可被利用”仍需结合球、朝向和跑动 |
| 运动 | 位移、速度、加速度 | 对平滑后的球场坐标求差分 | 切镜和标定跳变必须过滤物理异常值 |
| 转换 | 夺回后若干秒推进距离 | 从已确认球权转换点累计位移 | 球权转换事件本身不宜只靠二维判断 |
| 转换 | 阵型恢复时间代理 | 计算宽度、纵深恢复到球队常态区间的时间 | 只能称恢复代理，不能评价防守选择正确性 |
| 传球 | 已确认传球的长度与方向 | 对传球起止点计算距离和方向 | 前提是传球事件与起止点已经可靠确认 |
| 推进 | 已确认持球推进距离 | 对同一持球人的控制区间累计位移 | 前提是持球人和控制区间已确认 |
| 网络 | 已确认传球网络 | 以传球人/接球人为节点和有向边聚合 | 输入事件错误会直接污染中心性和传球熵 |

### 4.1 A 类不需要视觉大模型做什么

- 不让视觉模型凭画面估算精确距离、角度和速度。
- 不让视觉模型逐帧数所有球员再计算宽度和纵深。
- 不让视觉模型替代确定性的区域、多边形、距离和图统计代码。

视觉模型可以解释这些数字，但数值本身应由结构化坐标计算。

## 5. B 类：二维候选加视觉复核的能力

| 板块 | 技战术任务 | 二维投影能做什么 | 视觉模型必须补充什么 |
| --- | --- | --- | --- |
| 触球 | 稳定触球 | 找到球与球员距离极小的候选窗口 | 确认是否真实接触、遮挡下是否为同一人 |
| 接球 | Receive | 检测足球接近后降速且持球人稳定 | 确认接球动作、接球是否成功、是否发生争抢 |
| 传球 | Pass | 找到持球人切换和足球位移 | 确认真实踢球时刻、传球人、接球人和成功结果 |
| 传球分类 | 直塞、传中、转移 | 根据起止坐标、方向和防线位置产生候选 | 判断动作意图、传中方式、是否为解围或射门 |
| 持球 | Carry/Dribble | 跟踪持球人的位移和持续时间 | 区分稳定带球、失控追球、过人和无球跑动 |
| 球权 | 丢失、夺回、转换 | 通过最近球员和稳定窗口解码候选球权 | 排除争议球、折射、切镜、出界和比赛中断 |
| 射门 | 射门事件 | 依据进攻区域、球速、朝门方向筛选候选 | 确认踢球/头球动作、射门人、真实触球帧 |
| 射门结果 | 射正、偏出、封堵、进球 | 依据球门区域和后续轨迹提供弱证据 | 识别球是否入网、门将扑救、防守封堵和回放画面 |
| 射门结构 | 距离、角度、防守压力 | 对已确认射门计算几何和附近人数 | 确认射门身体部位、是否凌空、是否在对抗下完成 |
| 定位球 | 开出时刻与类型 | 检测球静止后运动、开出位置和轨迹 | 区分任意球、门球、界外球、开球和普通停顿 |
| 定位球 | 落点与后续结果 | 计算二维轨迹终点和下一稳定控球队伍 | 确认空中第一落点、争顶、二点球和真实控制者 |
| 防守 | 防守干预 | 从进攻中断、球权变化和距离关系产生候选 | 区分抢断、拦截、封堵、解围及是否触球 |
| 门将 | 出击/扑救候选 | 计算门将位置、移动方向、与球距离变化 | 确认扑救动作、是否触球、抱住/击出/漏球/失球 |
| 阵型 | 阵型代表帧 | 从完整远景帧拟合阵型层次 | 判断画面是否为回放、死球、近景或非正常比赛状态 |
| 压迫 | 高位逼抢候选 | 计算防守高度、持球人周围人数和接近速度 | 判断是否主动压迫、触发原因及是否迫使对手失误 |
| 防守空档 | 空档候选 | 识别低密度区域、线间距和防线身后空间 | 判断空间是否真的可利用、是否存在遮挡球员和跑动接应 |
| 进攻链路 | 一次进攻如何形成射门 | 连接已检测的传球、推进、进入和射门 | 修复切镜断链，确认关键动作和最终结果 |
| 比赛阶段 | 后场组织、推进、前场进攻 | 根据球区、队形和球权生成阶段候选 | 判断回放、暂停、反击、阵地进攻和长传争夺语义 |
| 高级模式 | 套边、内切、倒三角、肋部渗透 | 用轨迹形状和相对位置筛选候选 | 判断角色关系、动作时序和战术是否真正完成 |

### 5.1 B 类推荐输出方式

不应直接输出“系统确认发生”，而应保留两级状态：

```text
geometry_candidate
  -> visual_confirmed
  -> visual_rejected
  -> uncertain
```

每条结果至少保留：

- 二维规则分数。
- 视觉模型置信度。
- 支撑帧或视频时间窗。
- 模型选择的执行者和对象。
- `confirmed/rejected/uncertain` 状态。
- 规则与视觉结论冲突时的原因。

## 6. C 类：必须以视觉图片或视频为主的能力

| 板块 | 技战术任务 | 为什么二维投影不够 | 推荐视觉技术 |
| --- | --- | --- | --- |
| 球员身份 | 球衣颜色、号码、角色 | 坐标不包含外观和号码信息 | ReID、SigLIP/CLIP、OCR、多帧外观聚合 |
| 个人射门 | 支撑脚位置、摆腿、触球脚 | 需要关节和身体部位信息 | YOLO-Pose、RTMPose、视频动作识别 |
| 个人射门 | 躯干倾角、髋部旋转、随摆 | 轨迹只能看到人体整体位移 | 姿态估计加多帧关节角变化 |
| 头球 | 头球/争顶动作 | 二维脚点无法判断头部触球 | 人体关键点、球头相对关系、短时序模型 |
| 惯用脚 | 长期左/右脚倾向 | 需要大量可见触球脚样本 | 姿态、球员身份、长期片段聚合 |
| 门将动作 | 侧扑、倒地、高空接球、击球 | 需要手臂、躯干、起跳和落地姿态 | 门将动作模型、姿态估计、视频模型 |
| 对抗动作 | 抢断、铲球、碰撞、犯规 | 需要身体接触顺序和裁判后续判罚 | 多人姿态、动作识别、裁判信号/OCR |
| 高空球 | 球高、旋转、飞行弧线 | 单机位二维投影缺少深度 | 多视角/3D 球追踪；视觉模型只能做类别近似 |
| 争顶 | 卡位、起跳时机、头球精度 | 依赖身体姿态和空中球关系 | 姿态估计、球轨迹和多帧动作模型 |
| 技术规范性 | 射门/扑救/铲球是否规范 | “规范”需要动作证据和专家标准 | 姿态时序模型加教练标注规则 |
| 裁判事件 | 手势、出牌、哨停 | 坐标无法表达手势和卡牌 | 图像检测、动作识别、OCR |
| 比赛管理 | 比分、时间、换人信息 | 信息位于记分牌和字幕 | OCR、Action Spotting、官方标签 |
| 情境语义 | 回放、庆祝、受伤、死球 | 空间坐标可能与比赛动作相似 | 镜头分类、视频语义模型、音频辅助 |
| 教练级解释 | 选择是否合理、动作是否规范 | 需要战术背景、替代方案和专家标准 | 专项标注模型加人工审核，不宜只用通用 API |

### 6.1 单张图片仍然不够的任务

以下任务即使接入视觉模型，也必须提供多帧或短视频，不能只发送一张关键帧：

- 传球与射门的真实触球时刻。
- 抢断与被抢的先后关系。
- 门将出击、扑救和二次控制。
- 摆腿、触球、随摆等射门动作阶段。
- 头球起跳、触球和落地。
- 球权丢失与夺回。
- 高位逼抢触发和结果。
- 套边、内切、倒三角与第三人跑动。

## 8. 推荐的视觉 API 接入架构

### 8.1 总体工作流

```text
完整比赛视频
  -> 本地检测、跟踪、球队分类、球场标定
  -> 二维轨迹与规则分析器生成候选
  -> 候选前后截取 3-10 秒证据窗口
  -> 镜头类型与画质门控
  -> 原始帧 + 标注帧 + 二维结构化上下文
  -> 多模态视觉模型复核
  -> 规则分数与视觉分数融合
  -> confirmed / rejected / uncertain
  -> 前端人工复核与反馈
```

### 8.2 不建议整场直接调用 API

整场直接调用存在以下问题：

- 成本和延迟随视频长度快速增长。
- 长时序模型可能遗漏短暂触球事件。
- 通用模型对距离、速度和人数计数不稳定。
- 输出难以精确对齐到原视频帧。
- 同一问题重复调用可能产生不同结论。
- 比赛视频可能受到版权、隐私和服务条款限制。

更合理的方式是让二维分析器将 90 分钟压缩成数十到数百个候选窗口，再调用视觉 API。

### 8.3 每次调用建议提供的内容

1. 候选事件前 2-4 秒、后 3-6 秒的视频或均匀抽取的 8-16 帧。
2. 一组无叠加的原始画面，用于识别动作和结果。
3. 一组带球员框、球框、轨迹 ID 的辅助画面，用于指明分析对象。
4. 二维上下文 JSON：

```json
{
  "candidate_type": "shot",
  "candidate_time_sec": 128.4,
  "attacking_team": "team_0",
  "actor_track_id": 27,
  "ball_xy": [41.2, -7.6],
  "goal_direction": "positive_x",
  "nearest_defender_m": 2.4,
  "goalkeeper_track_id": 1,
  "rule_confidence": 0.72
}
```

5. 明确且有限的问题，例如：

- 是否发生射门，而不是传中或解围？
- 射门执行者是否为 `track_id=27`？
- 触球部位是左脚、右脚、头部还是无法判断？
- 结果是进球、门将扑救、封堵、偏出还是无法判断？

### 8.4 强制结构化输出

视觉模型应返回固定 JSON，不接受自由发挥式长文作为主结果：

```json
{
  "decision": "confirmed",
  "event_type": "shot",
  "event_subtype": "right_foot",
  "actor_track_id": 27,
  "outcome": "saved",
  "contact_frame_offset": 9,
  "evidence_frame_offsets": [7, 8, 9, 12],
  "confidence": 0.84,
  "uncertainty_reason": null,
  "short_reason_zh": "右脚触球后足球明显朝球门运动，门将随后将球挡出。"
}
```

必须允许模型返回：

```text
decision = uncertain
```

画面遮挡、足球不可见或镜头切换时，不应强迫模型给出确定标签。

## 9. 第一批推荐接入视觉模型的任务

按投入产出比排序如下。

### 第一优先级：L1 事实纠错

1. **射门/传中/解围三分类**：直接降低射门误报。
2. **射门执行者确认**：解决识别到旁边球员的问题。
3. **射门真实触球帧**：修复关键帧提前或滞后。
4. **射门结果确认**：进球、扑救、封堵、偏出和未知。
5. **定位球类型确认**：角球、任意球、门球、界外球、开球和点球。
6. **门将动作与结果确认**：出击、扑救、接球、击出和失球。
7. **防守干预子类型**：抢断、拦截、封堵、解围和未知。

这些任务会直接改善当前所有 P0-P3 下游指标，因为进攻链、射门结构、门将、转换和高光都依赖 L1 事件是否正确。

### 第二优先级：进攻组织语义

1. 直塞、传中和大范围转移复核。
2. Carry 与普通追球/无球跑动区分。
3. 高位逼抢触发与结果确认。
4. 防守空档是否被进攻方实际利用。
5. 进攻链跨切镜续接。

### 第三优先级：个人动作教学

1. 射门摆腿、支撑脚和随摆阶段。
2. 左脚、右脚和头球识别。
3. 门将侧扑、倒地、高空接球和击球。
4. 抢断和铲球动作证据。

该层应优先使用姿态估计和专项动作模型，通用视觉大模型主要负责解释，不应单独承担关节级测量。

## 10. 不应直接交给通用视觉 API 的结论

- 精确球速、跑速、距离和角度。
- 完整比赛的逐帧球员计数。
- 正式 xG、xA、xT 或 EPV 数值。
- 动作是否“规范”的最终评分。
- 球员是否做出了“最佳选择”。
- 犯规、越位和裁判判罚的最终法律式结论。
- 仅凭单个片段判断球员长期惯用脚或整体能力。
- 在足球不可见时推断完整传球链。

这些任务需要确定性计算、训练数据、官方标签或专家标准，不能依靠通用模型语言表达流畅就视为准确。

## 11. 置信度融合建议

可先采用可解释的规则融合：

```text
final_confidence
  = geometry_quality
  × tracking_quality
  × camera_quality
  × visual_confidence
```

推荐状态规则：

| 条件 | 输出状态 |
| --- | --- |
| 二维和视觉均高置信且一致 | `confirmed` |
| 二维高置信、视觉不可判断 | `candidate`，进入人工复核 |
| 二维低置信、视觉高置信 | `visual_candidate`，不可直接进入正式统计 |
| 二维和视觉明显冲突 | `conflict`，必须人工复核 |
| 画面质量差、球不可见或切镜 | `uncertain` |

不要简单对两个分数取平均。检测覆盖率、标定质量、镜头类型和遮挡程度应作为门控条件。

## 12. 推荐实施顺序

```text
第一步：保留现有二维分析器作为候选生成器
第二步：建立统一 evidence clip 和 evidence frame 导出接口
第三步：先接入射门、定位球、门将和防守干预四类视觉复核
第四步：把视觉输出写回统一 L1 事件契约
第五步：前端增加候选、视觉确认、冲突和人工确认状态
第六步：使用人工确认结果建立专项训练和评测集
第七步：再扩展传球子类型、压迫、防守空档和复杂战术模式
```

## 13. 最终判断

### 可以主要依靠二维投影

区域统计、平均站位、队形宽度/纵深/线距、紧凑度、阵型倾向、局部人数、距离速度、推进距离、传球网络和转换数值。

### 必须使用二维加视觉融合

触球、接球、传球、持球、球权转换、射门与结果、定位球类型与落点、防守干预、门将事件、压迫、防守空档、进攻链路和高级战术候选。

### 必须以视觉分析为主

球衣和号码、触球脚、射门姿态、头球、门将动作类型、身体对抗、抢断铲球、裁判信号、记分牌、动作规范性和教练级技术评价。

对当前项目最有价值的升级不是用视觉大模型替换二维分析，而是：

> **让二维系统高召回地找候选，让视觉模型高精度地做语义确认，再由人工审核处理冲突。**

## 14. DeepSeek 图像复核试验（2026-09-19）

本项目新增 `review_tactical_candidates_with_vision.py`，作为独立的 B 类事件复核入口。它读取现有 `tactical_analysis_report.json` 中的一个候选事件，默认在原始视频中截取候选前 2.5 秒至后 3.5 秒的 8 张顺序帧，也可用 `--before-sec`、`--after-sec` 和 `--frames` 调整密度；随后向支持图片输入的 `deepseek-flash` 发送原始帧和精简二维上下文，并保存单独的 JSON 结果。模型需返回 `confirmed`、`rejected` 或 `uncertain`，同时给出证据帧、置信度和中文理由；规则与视觉不一致时只产生冲突状态，不修改原始报告或计数。

这属于**图片序列复核试验，不是原生视频理解，也不是正式事件真值**。本版没有带 track ID 的标注帧，因此不允许模型确认具体 `actor_track_id`；没有球高、多视角和连续高帧率证据时，也不允许把“落点”或“扑救结果”写成确定事实。

### 14.1 运行方式

将密钥仅放在当前终端的 `DEEPSEEK_API_KEY` 环境变量中，不要写入命令行参数、Git 文件或前端代码。密钥属于敏感信息；已经在聊天中暴露的密钥应在平台轮换。每次 API 调用都会把选中的视频帧发送到服务商，**不得将受 SoccerNet NDA 限制的视频帧发送到外部 API**，除非协议明确允许。

```bash
conda activate sports
python review_tactical_candidates_with_vision.py \
  --report-json soccer_input_dataset/outputs/test_5min_current/l1_report_v1/tactical_analysis_report.json \
  --video soccer_input_dataset/test_5min.mp4 \
  --event-id event-0013 \
  --output-json soccer_input_dataset/outputs/vision_review_test_5min/event-0013.deepseek.json \
  --dry-run

# 确认本地证据时间窗后，设置 DEEPSEEK_API_KEY 并去掉 --dry-run 再运行。
```

接口采用 DeepSeek 官方 [图像理解指南](https://api-docs.deepseek.com/guides/vision/) 所述的 `deepseek-flash` 多图输入，以及 [Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/) 的 JSON 输出格式。模型名称和能力可能调整，运行前应复查官方文档。

### 14.2 本地试验结果

输入为非 SoccerNet NDA 的 `soccer_input_dataset/test_5min.mp4` 与相应 L1 报告；选取全片 10 个候选窗口进行实际调用，均成功返回结构化 JSON。其中 2 个传球候选获得视觉支持，8 个候选为证据不足、需人工复核：

| 候选 | 原二维输出 | 视觉复核 | 融合状态 | 主要原因 |
| --- | --- | --- | --- | --- |
| `event-0013`，19.567 秒 | 射门候选，规则置信度 0.96 | `uncertain`，视觉证据充分度 0.30 | `needs_human_review` | 抽帧未见明确射门触球；不能仅由轨迹速度认定为射门 |
| `set-piece-001`，54.133 秒 | 角球落点候选，规则置信度 0.7552 | `uncertain`，视觉证据充分度 0.35 | `needs_human_review` | 未见清晰的角球开出瞬间，第一落点和后续控制无法确认 |
| `event-0104`，77.767 秒 | 传球候选 | `confirmed`，视觉证据充分度 0.60 | `visual_supported_candidate` | 多帧可见普通短传动作 |
| `event-0332`，251.267 秒 | 射门候选 | `uncertain`，视觉证据充分度 0.25 | `needs_human_review` | 中场远景没有清晰射门触球证据，不能视作已确认射门 |
| `event-0345`，273.267 秒 | 传球候选 | `confirmed`，视觉证据充分度 0.72 | `visual_supported_candidate` | 多帧支持向前传球候选 |

规则分数和视觉证据充分度来自不同系统，均**不是经校准的事件概率**，不可相加或直接取平均。实际结果分别保存于 `soccer_input_dataset/outputs/vision_review_test_5min/`，供逐帧人工复核。此次没有证明模型提高了整体准确率；它证明了模型可以进入现有候选复核路径，并在证据不足时保留不确定状态。

下一步应针对疑似触球时刻加密抽帧，提供带 ID 的辅助帧，设计切镜门控，并用人工标注集衡量精确率、召回率及时间误差。只有评测通过后，才能把视觉支持的事件写回 L1 正式统计和网页展示。

### 14.3 五分钟试片

使用 `make_vision_review_video.py` 将原始比赛画面、原声、10 个二维候选和对应的视觉复核结果合成为一段连续视频。右侧显示当前节点的复核状态和原因，底部时间轴定位关键节点；未到达的节点只显示候选名称，不提前暴露模型结论。

```bash
conda activate sports
python make_vision_review_video.py \
  --video soccer_input_dataset/test_5min.mp4 \
  --reviews-dir soccer_input_dataset/outputs/vision_review_test_5min \
  --duration 300 --fps 20 \
  --output soccer_input_dataset/outputs/vision_review_test_5min/test_5min_deepseek_vision_review_full_v2.mp4
```

生成结果为 299.9 秒、1600×900、H.264/AAC。**五分钟是连续播放的原片时长，不代表视觉模型逐帧分析了五分钟**；外部 API 仅收到上述 10 个候选窗口的抽样图片，其余画面仍是未追加视觉结论的原始视频。
