# L1 事件层初步复现范围

更新日期：2026-09-07

## 1. 文档目的

本文档综合以下调研材料，确定足球技战术分析项目第一阶段需要正式复现的 L1 事件及产品输出：

- `技战术分析市场总结-四层框架组会版.md`
- `足球技战术分析平台调研报告（详细版）.md`
- `足球技战术分析调研.md`
- `docs/国内外足球技战术分析平台调研.md`
- 当前 `tactical_analysis/` 代码和视频分析流程

本文档用于约束第一阶段范围、统一事件定义、拆分开发任务和制定验收标准。

## 2. 核心结论

L1 事件层回答：

> 谁在什么时间、什么位置，完成了什么足球动作，动作结果如何。

完整分析链路为：

```text
比赛视频
  -> 球员、足球、球队和球场感知
  -> L1 事件事实
  -> L2 统计与价值模型
  -> L3 有球组织分析
  -> L4 无球与空间战术分析
```

第一阶段不追求复现 StatsBomb 或 Wyscout 的完整事件词典，而是先把高频、基础、可验证的事件做准，并保证每个事件可以回到视频证据。

| L1-02 | 定位球开始与落点 | 必做 | 定位球类型、开出位置、落点和后续结果 | 定位球质量、套路和高光 |

## 4. 六组核心事件定义

### 4.1 L1-01 射门与结果

#### 事件结构

```text
shot
├── goal
├── on_target_saved
├── off_target
├── blocked
├── hit_post
└── unknown
```

#### 必须输出

- 射门发生时间和证据帧。
- 射门球队和射门球员轨迹 ID；无法确认时允许为空。
- 射门起点球场坐标。
- 禁区内/外、左/中/右通道。
- 射门距离和可见球门角度。
- 射门结果及其置信度。
- 射门前持球人、传球或推进上下文。

#### 可选输出

- 左脚、右脚、头球或其它身体部位。
- 一脚射门、凌空、头球和远射等技术类型候选。
- 最近防守人、封堵人数和门将位置。
- `xg_lite` 或 `xg_context_proxy`。

#### 边界

- 第一阶段的 xG 仅用于同场候选排序，不称为正式概率模型。
- 射门不能只由足球速度阈值判断，应结合持球人动作、球的方向、进攻区域、球门位置和后续画面。
- 无法确认结果时必须输出 `unknown`，不能强行归类。

### 4.2 L1-02 定位球开始与落点

#### 事件结构

```text
set_piece_start
├── corner
├── free_kick
├── goal_kick
├── throw_in
├── kickoff
└── penalty
```

#### 必须输出

- 定位球类型、比赛时间、球队和开出位置。
- 足球由静止到明显运动的真实开出时刻。
- 传球方向、距离和第一稳定落点。
- 落点区域和下一控球队伍。
- 定位球后一定时间窗口内是否形成射门。

#### 边界

- 首版优先保证角球、门球和开球，随后扩展任意球、界外球和点球。
- 二维转播视频无法可靠获得球高、旋转和真实三维第一落点，应在报告中声明限制。

### 4.3 L1-03 Receive → Carry → Pass

该事件链是第一阶段最重要的连续有球单元：

```text
接球位置
  -> 稳定控制
  -> 持球移动
  -> 传球起点与终点
  -> 接球队员
  -> 球权结果
```

#### Receive 接球

- 接球时间、位置、球队和接球队员轨迹 ID。
- 对应的传球事件 ID。
- 接球成功、接球失败或无法确认。
- 接球时最近对手距离作为压力代理。

#### Carry 持球推进

- 起止时间、起止位置和持续时间。
- 总移动距离和向前推进距离。
- 起止区域及是否进入前场三区或禁区。
- 结束方式：传球、射门、被抢、出界或未知。

#### Pass 传球

- 传球人与接球人轨迹 ID。
- 起止时间、起止位置、长度和方向。
- 成功、失败、被拦截、出界或未知。
- 短传、中传、长传。
- 向前、横向、回传。
- 进入前场三区、进入禁区。

#### 可选子类型

- 直塞。
- 传中。
- 大范围转移。
- 关键传球和射门助攻。

首版可输出这些子类型的候选，但没有稳定真值前不纳入正式准确率承诺。

### 4.4 L1-04 球权丢失、夺回与转换

#### 事件结构

```text
possession_loss
ball_recovery
possession_change
high_turnover
```

#### 必须输出

- 原控球队伍、新控球队伍和涉及球员轨迹 ID。
- 丢失、夺回和稳定转换的时间。
- 事件发生位置和球场区域。
- 转换前后足球轨迹和持球确认状态。
- 夺回后 5 秒的向前推进距离。
- 是否进入前场三区、禁区或形成射门。

#### 边界

- 足球暂时丢失、镜头切换和比赛中断不能直接记为球权转换。
- 球权改变应经过候选、确认、释放和稳定窗口。
- `high_turnover` 需要明确统一进攻方向和对方半场阈值。

### 4.5 L1-05 基础防守干预

第一阶段先建立统一大类：

```text
defensive_intervention
├── block
├── interception
├── clearance
├── tackle
└── unknown
```

#### 必须输出

- 干预时间、位置、防守球队和防守球员轨迹 ID。
- 干预前的进攻动作。
- 干预后球权是否改变、足球是否出界。
- 子类型和子类型置信度。

#### 边界

- 当视觉证据无法区分抢断、拦截和解围时，只输出 `defensive_intervention`。
- 不以球员距离接近直接推断成功抢断。
- 滑铲动作规范性和犯规性质不属于第一阶段自动结论。

### 4.6 L1-06 门将面对射门与扑救结果

#### 事件结构

```text
goalkeeper_action
├── shot_faced
├── save
├── goal_conceded
├── claim
├── punch
├── rush_out
└── unknown
```

#### 必须输出

- 门将球队和轨迹 ID。
- 对应射门事件 ID。
- 射门发生时门将位置。
- 门将开始响应的时间和位置变化。
- 是否触球、控制足球、将球解围或失球。
- 扑救事件的证据时间窗口。

#### 边界

- 第一阶段只复现可观察的客观结果。
- 扑救动作是否规范、站位是否最优和技术评分暂不作为自动真值。
- 头球与门将飞扑必须结合角色、球门区域和射门上下文区分。

## 5. 辅助比赛结构事件

以下事件不是核心技战术动作，但会影响统计、比赛阶段和报告解释：

```text
period_start
period_end
kickoff
score_change
substitution
yellow_card
red_card
game_interruption
```

优先通过比赛画面、记分牌 OCR、裁判信号和官方标签融合获取。球员身份无法可靠确认时，允许先输出球队级事件。

## 6. 统一 L1 数据契约

所有事件检测器应输出统一结构，避免射门、传球和门将模块各自定义格式：

```text
event_id
period
timestamp_sec
frame
event_type
event_subtype
team_id
actor_track_id
recipient_track_id
start_x
start_y
end_x
end_y
outcome
confidence
evidence_start_sec
evidence_end_sec
source
review_status
related_event_ids
attributes
```

### 字段说明

| 字段 | 含义 |
| --- | --- |
| `event_type` | 主事件类型，如 `pass`、`shot` |
| `event_subtype` | 子类型，如 `long_pass`、`blocked` |
| `outcome` | `success`、`failure`、`unknown` 等结果 |
| `source` | `vision`、`ocr`、`official_label`、`manual` 或融合来源 |
| `review_status` | `candidate`、`confirmed`、`rejected`、`edited` |
| `related_event_ids` | 关联传球、接球、射门或门将事件 |
| `attributes` | 身体部位、压力、距离、方向等扩展属性 |

## 7. 建议处理流程

L1 不应由一个单帧分类器一次性完成，应采用共享感知结果下的多个事件检测器：

```text
视频解码与镜头分类
  -> 球员/足球检测与短时跟踪
  -> 球队、裁判、门将角色
  -> 球场标定与统一进攻方向
  -> 受约束球权状态机
  -> 并行事件检测器
       ├── 射门检测器
       ├── 定位球检测器
       ├── 传接带检测器
       ├── 球权转换检测器
       ├── 防守干预检测器
       └── 门将事件检测器
  -> 时序去重与事件关联
  -> 置信度校准
  -> 人工审核
  -> 统计、报告和高光
```

## 8. 第一阶段产品输出

### 8.1 结构化文件

- `event_timeline.json`
- `event_timeline.csv`
- `event_summary.json`
- `highlight_manifest.csv`
- `review_log.json`

### 8.2 网页输出

- 视频下方显示不同颜色的事件节点。
- 支持按射门、定位球、传接带、转换、防守和门将筛选。
- 点击事件跳转到对应时间。
- 右侧显示证据片段、事件属性和置信度。
- 支持确认、拒绝、修改类型、修改球队和调整时间边界。
- 人工修改后重新生成统计和报告。

### 8.3 分析成果

- 射门图和射门结果统计。
- 定位球开出与落点图。
- 传球方向、距离和区域统计。
- Receive → Carry → Pass 进攻片段。
- 球权转换和 5 秒推进片段。
- 基础防守干预区域图。
- 门将面对射门和扑救片段。
- 自动高光及中文比赛摘要。

## 9. 初步验收标准

应先建立至少 30 分钟人工标注测试集，覆盖远景、近景、回放、遮挡和镜头切换。

### 9.1 事件指标

- 每类事件统计 Precision、Recall 和 F1。
- 事件时间误差统计平均值和 95% 分位数。
- 球队归属、动作球员和接收球员分别统计准确率。
- 事件结果和事件子类型分别评测，不能与事件打点合并计算。

### 9.2 建议首轮门槛

| 指标 | 建议门槛 |
| --- | --- |
| 射门、进球和主要定位球事件 Precision | 不低于 85% |
| 射门、进球和主要定位球事件 Recall | 不低于 80% |
| 传球、接球、推进候选 F1 | 不低于 70% |
| 可见远景中的球队归属准确率 | 不低于 90% |
| 射门和定位球时间平均误差 | 不高于 1 秒 |
| 网页事件到证据片段跳转成功率 | 100% |
| 所有低置信事件 | 必须支持人工确认或拒绝 |

以上门槛是开发验收目标，不代表当前代码已经达到。

## 10. 当前代码基础与主要差距

当前 `tactical_analysis/analyzers/events.py` 已能输出：

- `touch_candidate`
- `receive_candidate`
- `carry_candidate`
- `pass_candidate`
- `possession_change`
- `shot_candidate`
- `corner_candidate`

本轮本地实现还新增或补齐：

- `TimelineEvent` 的子类型、结果、坐标、证据窗口、来源、审核状态和关联事件字段。
- `defensive_intervention_candidate` 基础防守干预候选。
- 角球、任意球、球门球、界外球、中圈开球和点球的几何分类入口。
- 定位球后 10 秒射门候选关联。
- `l1_event_timeline.json/csv`、`l1_summary.json` 和 `set_piece_manifest.csv`。
- 每个定位球一个 H.264 MP4 证据片段及 `set_piece_clips.json` 索引。
- 网页 L1 分类时间轴、定位球类型统计、独立片段播放和确认/拒绝接口。

当前已经具备 L1 原型，但尚不能视为正式事件真值。主要差距为：

1. 射门主要依赖足球速度、方向和区域规则，缺少可靠结果识别。
2. 定位球已有六类输出结构，但除角球外主要依赖几何规则，尚未达到稳定分类精度。
3. 传球成功主要由同队稳定持球人切换代理。
4. 球权转换未显式拆分丢失和夺回。
5. 基础防守干预已经输出统一大类，但抢断、拦截和解围子类型仍需专项模型或人工确认。
6. 门将事件尚未形成稳定客观结果分类。
7. 网页已支持确认和拒绝，事件类型、球队和时间边界编辑仍待补充。
8. 缺少按人工真值计算的事件级评测报告。

## 11. 暂不纳入第一阶段正式验收

以下功能可以保留为候选演示或研究模块，但不作为 L1 第一阶段复现完成的判据：

- 盘带过人及过人胜负。
- 地面对抗和高空对抗精细分类。
- 抢断、拦截、封堵和解围在低置信场景中的强制细分。
- 犯规类型、是否应该判罚和裁判决策评价。
- 越位和造越位战术。
- 详细压迫、反抢链和正式 PPDA。
- 门将扑救动作规范性和最优站位评价。
- 正式 xG、xA、xT、OBV 和 Pitch Control。
- 动态阵型、完整无球跑动和复杂战术套路。
- 惯用脚长期识别和教练级动作评分。

## 12. 推荐实施顺序

```text
第一步：扩展统一事件数据契约和人工审核状态
第二步：建立人工标注工具、标注规范和 30 分钟测试集
第三步：完成射门结果和主要定位球分类
第四步：稳定 Receive → Carry → Pass 和球权转换
第五步：增加基础防守干预和门将客观结果
第六步：加入事件去重、跨检测器关联和置信度校准
第七步：接入网页时间轴、证据片段和人工修正
第八步：通过 L1 验收后再升级 L2-L4 分析
```

## 13. 第一阶段完成定义

只有同时满足以下条件，才可以称为“L1 初步复现完成”：

1. 六组核心事件都有统一代码入口和统一数据结构。
2. 每个事件都有时间、位置、球队、结果、置信度和证据片段。
3. 无法判断的字段允许为 `unknown`，不会被规则强行填充。
4. AI 候选可在网页中确认、拒绝和修改。
5. 人工修改能够同步更新统计、报告和高光。
6. 在固定人工测试集上输出事件 Precision、Recall、F1 和时间误差。
7. 文档明确说明自动化边界，候选结果不冒充官方比赛真值。

第一阶段最终交付可以概括为：

> 复现射门、定位球、传接带、球权转换、基础防守干预和门将结果六条 L1 事件链，并基于这些事件生成可检索、可回看、可修正的时间轴、基础统计、中文报告和高光片段。
