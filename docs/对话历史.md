## 2. 项目目标与关键共识

用户希望把比赛视频处理成可以真正复盘的成果，而不是在视频上堆叠大量指标。目标链路为：

```text
比赛视频 / 已有视觉位置数据
  -> 球员与足球检测、跟踪、球队和角色识别
  -> 球场标定、二维坐标、统一比赛状态 GSR
  -> 共享时序上下文，各分析器分别产生事件与空间候选
  -> 原始画面与前后片段取证，可选视觉模型/人工复核
  -> 中文分析报告、事件索引、专题片段
  -> 本地网页联动播放、分层评语、按需阵型与个人选段
```

这不是一个端到端模型自动理解所有技战术，也不是每项研究都完成了论文复现。事件分析需要跨帧的人球关系与球权状态；阵型和空间分析需要可信的球场映射；个人动作需要原图、姿态和连续动作窗口。不同任务共享底层数据，但有各自的分析和证据流程。

“已实现”首先表示存在代码和输出，不等于已经达到官方比赛统计、跨比赛泛化或教练验收标准。

## 4. 用户长期偏好与纠错记录

- 主视频尽量保持原画面，只加人物与足球框；不要常驻大量文字、粒子、轨迹拖尾和复杂战术板装饰。
- 战术板重点是清楚展示两队分布；阵型框线只在查看阵型时出现，退出或切换后隐藏。
- 球员编号默认隐藏，启用才显示；编号不必等于球衣号，不要求跨出画/切镜后绝对一致，但同镜头在画人员应尽量稳定跟踪。
- 右侧片段和评语应有足够的纵向空间，避免可视区域过短；视频和事件节点要能相互跳转。
- 前端不直接显示抽象的 `L1/L2/L3/L4` 名称，分别使用“关键事件 / 数据统计 / 进攻组织 / 队形空间”。不要把助手或供应商名称作为前端卖点标签。
- 输出必须有可读结论和证据，不只是“多少帧属于某阵型”；暂停讲解曾要求缩短，应避免过多停顿和随肢体抖动的字幕。
- 先以定位球分类计数和完整切片服务后续分析，不强行加入尚无证据的发球质量评分。
- 用户曾提出“球出界即可完全置信定位球”，实现与解释必须保留边界：出界只能支持出界/重启候选，不能单独确认角球、任意球、最后触球队或重启结果。
- 门将事件不能只因门将存在就成立，应核对门区位置、球与门将持续接近及真实动作；脚下接回传不等于扑救，扑救不能误标为头球。
- 审核节点通常提供前后各约 5 秒的多帧证据；动作未覆盖时应扩大或加密窗口，而不是强行判定。
- 历史上曾要求保留某些好版本并新建文件试验，也曾明确允许直接修改。新任务先判断当前要求，不把旧的一次性编辑限制无限延续。
- 上传与本地处理应使用同一业务管线；样例缓存要与真正的新视频推理区分，不能用固定演示事件冒充新分析。

## 5. 当前已开发的分析范围

`configs/tactical_analysis.yaml` 启用 19 个统一分析器。P0-P3 是研发优先级，网页 L1-L4 是展示层级，两者不是一套编号体系。

| 能力块 | 当前功能 | 结果及限制 |
| --- | --- | --- |
| 质量门控 | 足球覆盖、可见人数、坐标质量 | 告知数据不足，避免低质量输入产生过强结论。 |
| 基础事件 | 触球、接球、传球、推进、射门、球权切换、出界、防守干预候选 | 时间轴与事件片段；主要依赖视觉规则与时序状态，不是完整结果真值。 |
| 定位球 | 重启、开出、后续控制/落点代理；类型计数和切片 | 类型不明保留未知；二维无法得到可靠球高、旋转和真实第一落点。 |
| 射门 | 位置、距离、角度、通道、压力、封堵与上下文分数 | `xg_context_proxy` 不是训练校准后的正式 xG。 |
| 进攻组织 | 传球方向/距离、短长传/直塞/传中、持球推进、穿线、阶段与进攻链 | 仅覆盖可见动作，切镜/漏球会截断链路；传球成功为视觉代理。 |
| 传球网络 | 有向连接、中心性、连通性、熵 | 身份不连续时网络解释受限。 |
| 阵型空间 | 平均站位、区域占用、阵型倾向、宽度/纵深/三线间距/紧凑度 | 支持代表帧与框线证据；不补画外球员，不把局部结构冒充完整阵型。 |
| 高级战术候选 | 局部多打少、压迫/PPDA 代理、防守空档、防守三区风险、攻防转换 | 已有几何和时序基线，尚无系统战术真值评测。 |
| 门将 | 接近来球、控球、出击及射门干预候选；近景分支 | 不能直接提供可信扑救成功率或规范性评分。 |
| 个人片段 | 临时编号、最多 30 秒同镜头选段、证据图和统计、已有审核例子 | 新选段不自动获得已确认语义结论；图像位移不是米制速度。 |
| 近景技术 | 姿态窗口、射门动作阶段、关键帧回看、中文解说 | 尚不能测真实肌肉发力、长期惯用脚或教练级动作评分。 |

过去曾总结“P0-P2 共 15 项有功能入口和输出”。正确理解是**功能覆盖**，不是 15 个专业任务均已可靠复现或达到成熟精度。完整说明见 [FEATURES.md](FEATURES.md)。

- 浏览器请求本地 Node API，后端通过 `conda run -n sports python -m ...` 执行 WSL 内代码，不是浏览器直接运行 Python。
- 个人选段后端支持 `SPORTS_PYTHON`，否则使用 Conda；不要重新写死开发机解释器绝对路径。
- `npm run build` 仅构建前端；静态托管或单纯打开 HTML 不能代替本地 API。
- 仅安装 Node 可以看界面；新视频推理仍需 Python、FFmpeg、模型权重与正确参数。
- 历史素材未随 Git 分发，克隆后旧项目不能播放通常是数据缺失，不一定是播放器故障。
- 本地服务缺少公网多用户认证、配额和隔离，只监听本机；不要未经加固对外发布。

## 13. 后续 TODO 与推荐顺序

这些是建议，不是本次已获授权的执行任务。

1. **评测优先**：建立多比赛人工真值，评估球检测、球队身份、球权、射门/定位球/门将事件的 Precision/Recall/F1、时间误差与跟踪稳定性。
2. **底层可靠性**：提升球召回与连续性，减少人球误判、蓝白混分、切镜 ID 污染、近景误用标定；加入更清晰的可见性和质量门控。
3. **证据窗口**：优先修正出界到重启、摆腿到触球、门将接球到出球等跨阶段切片，扩大窗口时避免混入别的镜头或回放。
4. **结果确认**：补可靠进球/射正/比赛中断及动作结果标签，不直接用高球速、二维邻近或事件数量计算专业成功率。
5. **稳定组织空间**：验证有球/无球和阶段条件阵型、传球类型、进攻链完整率、空档/压迫/转换候选，保留原图证据和拒识。
6. **可重复模型复核**：固定证据采样、提示、结构化校验与评测集，比较模型结果，不凭名字承诺与历史人工看图效果一致。
7. **工程交付**：按新任务需要补交打包工具、完善新机器安装与长视频资源管理；公网部署前增加认证、隔离和配额。
8. **长期研究**：数据充分后再推进校准 xG/xA/xT/EPV、完整 Pitch Control、长期身份/惯用脚、动作规范性和复杂战术模型。
