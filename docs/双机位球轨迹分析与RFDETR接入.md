# 双机位球轨迹分析与 RF-DETR/TCN 接入

更新日期：2026-09-20

## 1. 本次输入和边界

- 视频：`二维分析/分析视频2.mp4`，60 秒、25 FPS，含左右原始机位和右侧二维投影。
- 位置：`二维分析/weizhi.zip` 中的 `ball_positions.json` 与 `player_positions.json`。
- 球场：`二维分析/full_pitch_field_geometry.json`，长 101.2192 米、宽 65.0561 米。
- 球员空间统计继续复用现有 CSV 的双机位合并逻辑；不能将机位内 track ID 当作跨机位球员身份。

`weizhi.zip` 的足球有 1373 个观测点，覆盖 1500 帧的 91.5%。所给轨迹的所有球场坐标均在界内。这里的“0 段出界证据”是本段素材和这份坐标的事实，不代表比赛没有发生界外球；球在场外可能被漏检，或标定无法投影到场外。

## 2. 出界如何用于定位球

1. 使用原始检测点；TCN 补点不能单独证明越界。
2. 球场外至少 0.8 米、置信度至少 0.4，且连续至少 3 帧，标为“出界迹象”。这是一项保守的抗标定噪声门槛，不是足球规则里的球整体越线判定。
3. 穿过边线只能推“界外球候选”；穿过底线只能推“角球/球门球候选”。哪队最后触球、球是否越过球门线内侧、实际开球时刻，都需看原画面连续动作。
4. 候选片段要保留出界前和重新开球后的画面；仅在球离场的瞬间截片会漏掉定位球执行动作。

目前不能把坐标出界直接计为“已确认角球”或“已确认定位球开出”。二维投影是足球在地面的投影，腾空时可能投影越线而实际仍在比赛中。

## 3. 这段视频的可支持结论

- 12 个五秒窗口都输出足球区域、观测帧数及球员站位。
- 视频前约 35 秒足球在中圈附近几乎静止；约 35 秒后离开中圈，标为 1 段“中圈开球候选”，并切出开球前后证据视频，仍需原画面确认。后段球位置向右半场分布，40-45 秒足球观测覆盖明显下降。
- 蓝队可见球员整体宽度中位数约 33.5 米，红队约 27.8 米；这是可见站位，不是攻防优劣。
- 3 米内的最近球队仅为“近球关系候选”，不写成正式控球率、传球或进球。
- 连续场外投影 0 段，已确认定位球开出 0 次。不能因几何位置生成虚构角球片段。

输出位于 `二维分析/分析视频2_技战术结果/`，含 JSON、中文 Markdown、`l1_event_timeline.csv` 和中圈候选片段。网页“项目”中的“双机位足球与队形复盘”可同步播放原画面、查看关键事件候选时间轴、12 个空间时段与足球观测指标。

### 与 L1 事件层融合

本片的事件时间轴和空间指标共用同一套逐帧球、球员坐标及视频时间戳。`tactical_analysis/projection_l1.py` 先生成稳定近球区间，再按证据门槛产生事件候选，网页节点可直接跳到原画面：

| L1 组 | 本片候选 | 解读 |
| --- | ---: | --- |
| L1-01 射门与结果 | 0 | 没有足够踢球动作与球门结果证据 |
| L1-02 定位球开始与落点 | 0 | 没有可信角球、任意球证据；中圈开球不归此类 |
| L1-03 接球、持球与传球 | 5 | 都是连续近球候选，未确认实际触球 |
| L1-04 球权转换 | 0 | 不能用近球人切换替代球权变化 |
| L1-05 防守干预 | 0 | 缺少抢断、拦截或解围动作证据 |
| L1-06 门将事件 | 0 | 缺少门将触球/扑救证据 |
| L1-07 比赛结构 | 1 | 中圈开球候选，仍待原画面确认 |

合计 6 个**待复核候选**，已确认比赛事件为 0。开球前静止阶段不生成触球候选；不同机位的 track ID 不跨镜头拼接为传球关系。空间站位、近球关系和 L1 节点在同页呈现，但不能把“同页呈现”理解成事件分类模型已完成真值验证。

### 两种输出布局

- `分析视频2_全景技战术.mp4`：完整 60 秒，保留两个机位与二维球场图并排；下方同步显示中文事件名称与当前 5 秒空间指标，不在可视化中显示 L1 编号。
- `分析视频2_主机位预览.mp4`：完整 60 秒，机位一占主画面，机位二小窗与二维球场图固定在独立右栏；下方保留同一份事件和空间分析。这是可离线播放的**固定机位预览**，MP4 本身不能点击切换。
- 网页“切换视角版”：共用原视频和报告，点击右侧小窗可把机位一、机位二互换为主画面；二维球场图一直在侧栏，不覆盖主画面。可播放、暂停、拖动、调音量和全屏；“全景分析版 / 切换视角版 / 原始拼接”切换时保留时间位置。

两种成品均无额外暂停，事件时间戳与原片一致。`L1-xx` 只保留在 JSON/CSV 的内部分类字段中，网页和视频显示“中圈开球候选”“近球控制候选”等直白名称。

## 4. 新足球检测后端

原球员跟踪与球队分类不变；新视频的足球轨迹可由 `API.zip` 提供的 **RF-DETR + Global SAHI + 双向 TCN** 推理包生成：

```text
原视频/截取帧
  -> RF-DETR + SAHI 足球候选框
  -> TCN 补全未检出帧
  -> trajectory.jsonl
  -> ball_detection_adapter.py 合并进 SoccerNetGSR JSON
  -> 原可视化与技战术分析流程
```

`run_local_video_gsr_visualization.py` 默认使用 `--ball-backend rfdetr-tcn`；旧版可用 `--ball-backend legacy`。有已计算轨迹时用 `--ball-trajectory PATH` 避免重复推理。`API/model/` 中两份权重来自用户提供的 `API.zip`，被 `.gitignore` 排除；在新机器上需自行放入，不能从 Git 仓库下载到权重。不要把 `API.zip` 或权重提交到公开仓库。

环境（已在本机 `sports` 中安装并完成短片实跑）：

```bash
conda activate sports
python -m pip install rfdetr==1.9.2 sahi==0.11.36
python API/run.py --input /path/to/clip.mp4 --output-dir /path/to/ball_output
```

12 帧近景短片的独立推理结果为 6 帧 RF-DETR 直接检出、6 帧 TCN 补全。另取 12 帧可见完整球场的远景，端到端跑通原 GSR 管线：保留 168 条人物记录、将 12 条旧足球记录替换成 12 条 RF-DETR 足球记录，并生成 12 帧可视化视频。近景单独送入完整 GSR 时，原球场关键点模块因看不到场地而失败；新足球后端本身可在近景推理，但完整战术投影仍要求可见/可标定球场。上述短片仅用于连通性验收，不是检测精度评测。RF-DETR 对全分辨率视频逐帧做 SAHI，长视频处理会显著慢于旧球检测。
